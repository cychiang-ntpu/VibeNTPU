# 課程規劃：學習目標、進度與評量

[← 回課程首頁](../README.md)

本文件說明本單元的學習目標、上課進度、評量方式與權重、分析式評分規準、AI 使用規範與課堂規範。評量標準於開課前公開，目的在於讓學生事先理解「什麼是高品質的成果」，而非事後才得知評分依據。

---

## 1. 學習目標

學習目標依 Anderson 與 Krathwohl（2001）修訂之布魯姆分類法（Bloom's revised taxonomy）撰寫，每一項均以可觀察的動詞描述，並對應至課堂活動與評量證據（建構式對準，constructive alignment）。

| 編號 | 學習目標 | 認知層次 | 主要學習活動 | 評量證據 | 檢核點 |
| --- | --- | --- | --- | --- | --- |
| LO1 | 依據社群媒體 SaaS 架構圖，解釋一次「按讚」操作所經過的服務與資料流 | 理解 | 架構講義、互動教材、預測—觀察—解釋（POE） | 架構互動測驗正確率 80% 以上 | 1 |
| LO2 | 區分前端、版本控制、雲端託管、後端即服務（BaaS）四個元件的職責 | 理解／分析 | 美食街類比轉換為技術術語、小組討論 | 測驗；發表中的架構說明 | 1、7 |
| LO3 | 使用 VS Code 與 GitHub Copilot 產生並修改符合自訂題目的單頁網站 | 應用／創造 | 教師示範、提示詞產生器、獨立修改 | 可預覽的 `index.html`；AI 使用紀錄 | 2 |
| LO4 | 以 Git 完成 clone、stage、commit、sync，並將 GitHub repo 連接 Netlify 部署 | 應用 | 步驟卡實作、配對程式設計 | GitHub commit 紀錄；Netlify 公開網址 | 2、3 |
| LO5 | 串接 Netlify Forms 收集使用者資料，並說明資料流向與個資保護責任 | 應用／評鑑 | 表單串接、資料流互動教材、個資討論 | 後台收件紀錄（遮蔽個資之截圖）；自我檢核 Level 2 | 4 |
| LO6 | 比較 LocalStorage 與伺服器端資料庫在安全性、持久性與適用情境上的差異 | 分析 | 實作會員狀態、開發者工具觀察、比較表 | 自我檢核 Level 3；學習單比較題 | 5 |
| LO7 | 透過實際修改與自動部署，說明 CI/CD 對迭代速度與品質的影響 | 理解／評鑑 | 修改 → Commit → Sync → 觀察自動部署 | Netlify 部署紀錄與對應 commit；反思 | 6 |
| LO8 | 以問題、解方、架構與驗證數據建構一段 1 分鐘的 MVP 發表 | 創造 | 發表模板、同儕回饋、作品巡禮 | 發表表現（依評分規準） | 7 |

## 3. 評量方式與權重

| 評量項目 | 權重 | 評量內容 | 證據來源 |
| --- | --- | --- | --- |
| 第 1 週成果 | 20% | 網站已公開上線（10%）；內容切合題目且行動裝置可讀（10%） | Netlify 網址；自我檢核 Level 1 |
| 第 2 週成果 | 30% | 表單可正常收件（10%）；會員狀態畫面（10%）；至少一次 CI/CD 更新紀錄（10%） | Netlify 後台；自我檢核 Level 2、3；GitHub Commits 頁面 |
| 學習歷程檔案與反思 | 10% | 每週反思完整度與具體程度；AI 使用紀錄 | 學生 repo 中的 [學習歷程檔案](../templates/portfolio_README.md) |
| 市場驗證 | 10% | 取得非同學之目標使用者回應，並提出基於數據的觀察 | 學習歷程檔案之市場驗證紀錄 |
| MVP 發表 | 30% | 問題與解方、架構說明、Demo、驗證證據 | 課堂發表（依第 4 節規準） |

說明：

1. 反思不評文筆，而評「是否具體」：能指出具體事件、錯誤、解決過程與尚未理解之處者，即可取得滿分。
2. 市場驗證評的是方法與觀察的品質，不以名單數量排名。
3. 檢核點用於提供學習回饋，本身不另計分；評分以上表證據為準。

## 4. 分析式評分規準

以下規準適用於週成果與 MVP 發表。每項準則依三個表現等級描述，對應 [示範作品](../samples/README.md) 的 LOW、MEDIUM、HIGH。「基礎」即達及格標準。

| 評分準則 | 基礎（LOW，及格） | 良好（MEDIUM） | 優秀（HIGH） |
| --- | --- | --- | --- |
| 1. 問題與價值主張 | 有產品名稱與一句話介紹，但目標使用者與問題描述籠統 | 明確指出目標使用者及其具體困擾，功能與困擾有對應關係 | 問題描述具體且有證據支持（例如訪談、觀察或公開資料），價值主張能說明與既有替代方案的差異 |
| 2. 介面與使用者體驗 | 頁面可正常顯示，含標題、說明與行動呼籲（Call to Action, CTA）按鈕 | 版面結構完整（導覽、主視覺、功能、價格、常見問題），行動裝置可正常閱讀 | 具一致的視覺識別；互動回饋明確（送出成功或失敗訊息）；考量可及性（對比、字級、表單標籤） |
| 3. 功能實作 | 網站部署於 Netlify 並可公開存取（Level 1） | 表單可將資料送至 Netlify Forms 並於後台查看（Level 2） | 以非同步請求送出表單並以 LocalStorage 呈現會員狀態，含登出與錯誤處理（Level 3） |
| 4. 版本控制與部署流程 | repo 存在且有初始 commit | 有多次 commit，訊息可辨識修改內容；Netlify 與 GitHub 已連接 | commit 訊息清楚描述每次修改的目的；可指出某次 commit 與對應部署紀錄，說明 CI/CD 流程 |
| 5. 架構說明與取捨 | 能說出網站託管於 Netlify | 能正確說明四個元件的職責與資料流 | 能說明架構選擇的理由與限制（成本、速度、安全性、擴充性），並提出下一階段的技術演進方向 |
| 6. 驗證與資料倫理 | 表單可運作，但僅有同學測試資料 | 有非同學之目標使用者回應，並能描述觀察 | 以數據（例如轉換率）支持結論；清楚告知資料用途；發表時妥善遮蔽個資 |

## 5. AI 使用規範

本課程鼓勵使用生成式 AI，但使用者須對產出負完全責任。以下規範參照一般學術誠信原則訂定。

### 5.1 揭露（Disclosure）

- 於學習歷程檔案的「AI 使用紀錄」記錄所使用的工具、用途、主要提示詞與自己所做的修改。
- 發表時如有 AI 產生的文案、圖片或數據分析，應予說明。

### 5.2 驗證（Verification）

- AI 產生的程式碼須實際預覽與測試；發表時應能說明各主要區塊的作用。不理解之處可使用 Copilot 的 Ask 模式請其解釋。
- AI 產生的事實陳述（例如市場規模、統計數字、法規）須查證原始來源；無法查證者不得作為論據。
- AI 可能產生不存在的套件、網址或 API，也可能引入安全問題（例如將資料寫入公開位置）；使用前應檢查。

### 5.3 隱私（Privacy）

- 不得將他人個人資料（姓名、Email、電話、表單收件內容）貼入 AI 對話。
- 不得將密碼、存取權杖（token）、驗證碼提供給 AI 或貼入程式碼。
- 網站收集資料時應在表單附近說明用途；發表截圖須遮蔽個資。相關法規可參考《個人資料保護法》。

### 5.4 學術誠信（Academic Integrity）

- Git 的 Commit 與 Sync 請自行於「原始檔控制」面板操作，不要交由 Copilot 代為執行；這是本課程要求學生掌握的技能。
- 反思與市場驗證觀察須為本人撰寫，不得由 AI 代寫。
- Demo 可使用虛構資料，但須明確標示；對外宣傳與發表中的驗證數據必須真實。

## 6. 課堂規範

| 規範 | 說明 | 目的 |
| --- | --- | --- |
| 配對程式設計 | 兩人一組，駕駛（driver）操作電腦，導航員（navigator）對照步驟卡、檢查輸出並提醒下一步；每個實作段落交換角色 | 降低單人錯誤率，促進說明與討論 |
| 課堂即時回饋卡 | 完成當前步驟貼綠色，需要協助貼紅色；助教主動巡視紅色卡 | 提供不需舉手的求助管道 |
| 15 分鐘求助原則 | 同一問題自行嘗試 15 分鐘無進展即求助 | 避免無效卡關 |
| 求助順序 | [疑難排解手冊](tutorials/error_guide.md) → Copilot Ask 模式（附錯誤訊息）→ 同儕 → 助教或 [求助單](https://github.com/cychiang-ntpu/VibeNTPU/issues/new?template=help_request.yml) | 培養自主除錯能力 |
| 尊重與回饋 | 作品巡禮以「我喜歡／我希望／如果」三句式提供具體、友善的回饋 | 建立心理安全感 |
| 個資保護 | 投影與截圖前確認畫面不含他人個資 | 落實資料倫理 |
